When Devsy connects to an environment through a provider, it injects itself there. This counterpart is the Devsy agent. It is the same binary, run as `devsy agent`. The agent deploys the container, forwards credentials, runs the SSH server and stops idle environments.

The `agent` section of `provider.yaml` controls how Devsy works with it.

```yaml
agent:
  path: ${DEVSY}
  local: true
  driver: docker
  inactivityTimeout: 10m
  containerInactivityTimeout: 10m
  injectGitCredentials: ${INJECT_GIT_CREDENTIALS}
  injectDockerCredentials: ${INJECT_DOCKER_CREDENTIALS}
  binaries:
    MY_BINARY:
      - os: linux
        arch: amd64
        path: https://example.com/my-binary
        checksum: <sha256 of the file>
  exec:
    shutdown: |-
      ${MY_BINARY} stop
```

Option values can be used in this section.

- **path**: where the agent is placed on the remote machine.
- **local**: set to `true` when Devsy runs directly on this machine instead of reaching a remote one. The built-in providers do this.
- **driver**: how the container is deployed. One of `docker` (default), `kubernetes`, `apple`, `microsandbox`, `custom` or `external`. See [Drivers](./driver.mdx).
- **inactivityTimeout**: how long to wait before stopping an idle machine. For machine providers.
- **containerInactivityTimeout**: how long the container may be idle before it stops. A Go duration such as `10m`; empty or `0` disables it. For non-machine providers.
- **injectGitCredentials**, **injectDockerCredentials**: whether to copy those credentials into the environment.
- **exec.shutdown**: the command that stops the machine once it is idle. Option values are available in it.
- **binaries**: helper binaries for `exec.shutdown`. Same format as [provider binaries](./binaries.mdx).

## Stopping idle environments

Devsy tracks whether anyone is connected and stops the environment after the timeout. Devsy starts it again when the user returns. State persists only if the provider preserves the storage. A shutdown command that deletes the machine must keep workspace data separately, for example on a persistent volume.

### Non-machine providers

Set the timeout with `containerInactivityTimeout`. It is a Go duration such as `10m`; empty or `0` disables it.

On the `kubernetes` driver, the Devsy daemon is the pod's main process. SSH, hooks and setup obtain acknowledged protection over a persistent Unix socket before doing work. Setup suspension belongs to that connection, so a dead setup process cannot leave the timer suspended indefinitely; loss of the owner connection aborts the client work. The daemon exits normally when the workspace has been idle for the timeout, ending the pod while keeping its volume. Other container drivers start a detached daemon whose exit does not by itself stop the container. See [Auto-Inactivity Timeout](../developing-in-workspaces/inactivity-timeout.mdx#kubernetes) for activity rules and pod-layout restrictions.

The managed activity socket is container-local, not host remote-access IPC. Its `0666` transport permissions let non-root workspace processes register activity under a root daemon; the owner checks kernel peer UID/PID and process-start identity, and only root or the daemon's own UID can change setup or timeout policy. Any local container user can keep a live activity registration, so this is not an authorization boundary against untrusted code already running in that container. Do not expose the socket outside the container. Host remote-access owner IPC retains its separate `0600` policy, and workspace authorization remains context plus workspace UID at the existing tunnel boundary.


### Machine providers

Stopping only the container would leave the VM running and billed. Define `agent.exec.shutdown` with the command that stops or deletes the machine on the cloud side. Set the timeout with `inactivityTimeout`. The official cloud providers each do this their own way, for example with a cloud API call using a token saved in an option.
