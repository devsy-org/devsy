## Stop a workspace

Stopping pauses a workspace so it stops using CPU and memory. Depending on the provider, Devsy stops the container or shuts down the VM it runs on. The data is kept.

In Devsy Desktop, open the workspace actions menu and choose **Stop**. From the CLI, run:

```sh
devsy workspace stop my-workspace
```

To start it again, run:

```sh
devsy workspace up my-workspace
```

Some providers stop idle workspaces on their own. See [Auto-inactivity timeout](./inactivity-timeout.mdx).

Stopping or deleting a workspace first cancels its running `devsy workspace up --detach` task. To cancel a task yourself, run `devsy workspace task cancel <task-id>`.

## Delete a workspace

Deleting removes the workspace and all data Devsy stores about it. Depending on the provider, Devsy removes the container or deletes the VM.

In Devsy Desktop, open the workspace actions menu, choose **Delete**, and confirm. If the delete fails, the workspace detail page shows the error and links to the logs.

From the CLI, run:

```sh
devsy workspace delete my-workspace
```

`devsy workspace down` and `devsy workspace rm` are aliases for the same command.

If the provider is unreachable, force the delete:

```sh
devsy workspace delete my-workspace --force
```

With `--force`, Devsy continues past several teardown errors:

- Container deletion, including machine providers without `autoDelete`: Devsy ignores a failed container teardown and logs errors other than a deadline timeout. If Devsy cannot check the machine status, it skips the container teardown.
- Auto-delete machines: Devsy logs a failed machine delete command and continues.
- Daemon-backed workspaces: Devsy still tries to delete the instance. It logs delete request errors other than NotFound and continues. Waiting for deletion can still return an error.

Provider resources can remain after a forced delete.
