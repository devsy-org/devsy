A workspace is a containerized development environment with a project's source and its tools. A [provider](../managing-providers/what-are-providers.mdx) creates the environment.

Devsy uses the [devcontainer.json](https://containers.dev/) format, which VS Code dev containers and GitHub Codespaces also use. A project with a `devcontainer.json` needs no extra setup. Without one, Devsy detects the project's language and offers a template.

A workspace keeps its state when you stop and restart it. While it runs, it accepts SSH connections at `WORKSPACE_NAME.devsy`. Devsy opens it in a local IDE if you select one.

## Create a workspace

The source can be a Git repository, a local folder, or an image such as `golang:latest`.

### Devsy Desktop

Open **Workspaces** and click **Create**. The wizard has five steps:

1. **Provider.** Pick an initialized provider. You cannot change it later.
2. **Source.** Pick a template or an image, or enter a Git URL, image, or local path. **Show advanced options** lets you set the branch, commit, or PR, a project subfolder, the folder to open, the `devcontainer.json` path, and a prebuild repository.
3. **IDE.** Optional. The default is none.
4. **Review.** Check the workspace name and configuration. If the image has no build for your architecture, you can turn on **Run under emulation**.
5. **Launch.** Devsy creates the workspace and streams progress, then opens your IDE if you selected one.

The desktop app runs `devsy workspace up` for you.

### Workspace IDs

The workspace name is its ID. Use lowercase ASCII letters (`a-z`), digits (`0-9`), and hyphens (`-`), with a maximum of 48 characters.

Desktop suggests a valid ID from your source. A local folder named `Backend` gets the suggestion `backend`. The source path keeps its original case. If you enter a name yourself, it must follow the same rules:

```sh
devsy workspace up ./Projects/Backend --id backend
```

<Callout title="Workspace IDs">
Uppercase workspace IDs are rejected before creation starts. Startup failures appear as failed tasks in Desktop.
</Callout>

### Devsy CLI

[Install the CLI](../getting-started/install.mdx#install-devsy-cli), then add a provider. This example uses Docker:

```sh
devsy provider add docker
```

**Git repository**

```sh
devsy workspace up github.com/microsoft/vscode-remote-try-node
```

Add `@` and a ref to pick a branch, commit, or pull request:

```sh
devsy workspace up github.com/microsoft/vscode-remote-try-node@main
devsy workspace up github.com/microsoft/vscode-remote-try-node@sha256:15ba80171af11374143288fd3d54898860107323
devsy workspace up github.com/microsoft/vscode-remote-try-node@pull/108/head # GitHub only
```

Devsy forwards your Git credentials, so private repositories work. Use `--id` to name the workspace and create several from one repository.

**Local folder**

```sh
devsy workspace up ./path/to/my-folder
```

Devsy copies the folder to the provider and builds from its `devcontainer.json`. See [.devsyignore](#devsyignore) to exclude files.

**Image**

```sh
devsy workspace up ghcr.io/my-org/my-repo:latest
```

Devsy generates a `devcontainer.json` that names the image. To run an image built for another architecture, add `--platform linux/amd64`. Emulation is slower, so prefer multi-arch images.

Desktop also lists ready-made images and marks the ones that do not fit your machine.

**Existing container**

```sh
devsy workspace up my-workspace --source container:$CONTAINER_ID
```

Only the `docker` provider supports this, and `--recreate` is rejected for these workspaces.

<Callout title="Devsy home">
Pass `--home=PATH` or set `DEVSY_HOME` to change where Devsy keeps its data. Use this on WSL if a workspace tries to mount a Windows path instead of a path inside WSL.
</Callout>

## Read setup output

Devsy keeps the output of the build and each lifecycle hook, such as `postCreateCommand`, after `devsy workspace up` finishes. To read it:

```sh
devsy workspace logs WORKSPACE_NAME --source setup --list
devsy workspace logs WORKSPACE_NAME --source setup --run RUN_ID --result-format=plain
```

The run ID appears in the result of `devsy workspace up` and in the output of a detached creation task. Use `--list` to find IDs for earlier runs.

- Hooks that run after `waitFor` (default `updateContentCommand`) can finish after `up` returns. Their output joins the same run. Add `--follow` to watch them.
- A hook that an earlier attempt already marked is skipped with the reason `already_attempted`. This does not mean the earlier attempt succeeded. Check that run.
- `postAttachCommand` runs on every attach. Each run is recorded separately.

See [Troubleshooting](../troubleshooting/troubleshooting.mdx#find-the-right-log) for all options and [Setup history](../troubleshooting/setup-history.mdx) for limits and redaction.

## .devsyignore

Put a `.devsyignore` file in the root of a local workspace folder to leave files out of the upload when Devsy uploads the folder to the provider, as it does for Kubernetes. The file uses [Docker ignore syntax](https://docs.docker.com/build/concepts/context/#dockerignore-files). Paths are relative to the folder. The last matching rule wins.

```text
big/
**/node_modules/
docs/*.tgz
build/
!build/keep.txt
```

- A missing or empty file uploads everything.
- An unreadable file or invalid pattern stops the upload with an error naming the file.
- The file filters only the workspace folder upload. Extra bind mounts, local Docker bind mounts, and image builds follow their own rules. After a Git clone, Devsy deletes the paths the file lists, matched literally. Devsy does not read `.gitignore` or `.dockerignore`.

## Inspect a workspace

```sh
devsy workspace describe my-workspace
```

This prints the configuration and live state. Add `--result-format json` for scripts. Related commands:

- `devsy workspace status <name>` shows whether it is running or stopped.
- `devsy workspace logs <name>` streams the agent logs.
- `devsy workspace ping <name>` checks that the agent is reachable.
- `devsy workspace troubleshoot <name>` bundles diagnostics for an issue report.

## Recreate a workspace

Recreating applies changes to `devcontainer.json` or its Dockerfile. If a prebuild repository is configured, Devsy looks there for the new image first.

```sh
devsy workspace up my-workspace --recreate
```

<Callout type="warn">
Recreating keeps only the project folder and mounted volumes. Anything else in the container is lost.
</Callout>

## Reset a workspace

A reset pulls the latest Git changes, or uploads your local folder again. For local-folder workspaces, Devsy removes and re-seeds its managed named volumes. Bind mounts and unmanaged volumes stay.

```sh
devsy workspace up my-workspace --reset
```
