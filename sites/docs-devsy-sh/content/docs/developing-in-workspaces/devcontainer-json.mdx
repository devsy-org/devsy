Devsy uses the [open `devcontainer.json` standard](https://containers.dev/) to define a project's development container. VS Code and GitHub Codespaces use the same format, so existing configurations work in Devsy.

If a project has no configuration, Devsy detects the language and uses a default.

For the full format, see the [reference](https://containers.dev/implementors/json_reference/), the [VS Code documentation](https://code.visualstudio.com/docs/devcontainers/create-dev-container), and the [Codespaces documentation](https://docs.github.com/en/codespaces/setting-up-your-project-for-codespaces/adding-a-dev-container-configuration/introduction-to-dev-containers#devcontainerjson).

## Where the file lives

Devsy looks for one of:

- `.devcontainer/devcontainer.json`
- `.devcontainer.json`
- `.devcontainer/<folder>/devcontainer.json`

To use a specific file, pass its path:

```sh
devsy workspace up github.com/my-org/my-repo --devcontainer ./path/to/devcontainer.json
```

Use `extends` to inherit from other files. It takes a path or a list of paths. Keep the files a configuration depends on inside its folder.

### Existing workspaces

Devsy remembers which configuration each workspace uses. If a later search finds a different file, Devsy warns and keeps the saved one. To switch files, recreate the workspace:

```sh
devsy workspace up <workspace> --recreate --devcontainer "<relative-path>"
devsy workspace up <workspace> --recreate --devcontainer "id:<name>"
```

Devsy saves the choice for later runs.

## Dockerfile

```json
{
  "build": {
    "dockerfile": "Dockerfile"
  }
}
```

## Docker Compose

Set `dockerComposeFile` to one or more Compose files. Set `service` to the service that runs as the dev container:

```json
{
  "dockerComposeFile": ["docker-compose.yml", "docker-compose.dev.yml"],
  "service": "backend"
}
```

Devsy names the Compose project the same way Docker Compose does, so it reuses a project that is already running. It checks these sources in order:

1. `COMPOSE_PROJECT_NAME` in your shell.
2. `COMPOSE_PROJECT_NAME` in an `.env` file, in the devcontainer folder, the workspace root, or a compose file's folder.
3. The top-level `name:` in the compose files. The last file that sets it wins.
4. A name derived from the workspace.

The `name` field in `devcontainer.json` is only a display name and never names the compose project.

A custom `DOCKER_HOST` set for the Docker provider is passed to the `docker compose` commands Devsy runs.

## Features

[Features](https://containers.dev/features) are reusable pieces that Devsy merges into your Dockerfile, such as `docker-in-docker` or `kubectl`.

To send HTTP headers when Devsy downloads a feature archive, set them under `customizations`:

```json
{
  "features": {
    "https://example.com/foo_feature.tar.gz": {}
  },
  "customizations": {
    "devsy": {
      "featureDownloadHTTPHeaders": {
        "FOO_HEADER": "${localEnv:FOO_ENV_VAR}",
        "BAR_HEADER": "bar"
      }
    }
  }
}
```

## Applying changes

After you edit the configuration, apply it without deleting the workspace:

```sh
devsy workspace up my-workspace --recreate
```

Devsy builds and validates the new image before stopping or replacing the existing container. If the build fails, the existing workspace stays in its previous state, whether running or stopped. A later failure can leave the old container stopped or removed, depending on the provider. Pass `--recovery` to start a recovery container with features and lifecycle commands disabled if the build fails.

<Callout type="warn" title="Recreating">
Anything outside volumes is lost. The project folder and other mounted paths stay.
</Callout>

## postStartCommand and waitFor

`waitFor` names the lifecycle hook that `devsy workspace up` waits for before it returns. The default is `updateContentCommand`, so `postStartCommand` can finish after `up` returns.

A `postStartCommand` that asks for input needs an attached terminal. Add `--interactive-post-start` to that `devsy workspace up` run. The option does not change `waitFor` in this file. For the details and limits, see [Answer prompts in postStartCommand](./create-a-workspace.mdx#answer-prompts-in-poststartcommand).

## Environment variables in devcontainer.json

With the SSH provider, the variable in `${localEnv:NAME}` must reach the remote machine.

1. Reference the variable in `devcontainer.json`:

   ```json
   {
     "name": "Node.js",
     "image": "mcr.microsoft.com/devcontainers/javascript-node:${localEnv:IMAGE_VERSION}"
   }
   ```

2. Send it from your local `~/.ssh/config`:

   ```
   Host <REMOTE-SSH-SERVER>
      SetEnv IMAGE_VERSION=0-18-bullseye
   ```

3. On the remote machine, add `AcceptEnv IMAGE_VERSION` to `/etc/ssh/sshd_config` and restart the SSH service.

4. Start the workspace:

   ```sh
   devsy workspace up <GITHUB-REPOSITORY-URL> --provider ssh --ide=none
   ```
