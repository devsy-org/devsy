Known issues and fixes on Linux.

### Files owned by an unknown user after using a local folder

When you start a workspace from a local folder and `devcontainer.json` sets `remoteUser` or `containerUser`, Devsy changes the folder's ownership to that user so the container can write to it. On the host the owner then shows as an unknown user. After the workspace stops, restore it:

```sh
sudo chown -R $(id -un):$(id -gn) .
```

Local folders suit early work. Once the devcontainer works, push it to a Git repository and use that instead.

### SSH host login shells

The SSH provider supports Bash, Zsh, and Fish login shells on Linux. Agent installation runs through the host's executable `/bin/sh`; interactive terminals and environment probing continue to use the account's configured shell. The workspace container's shell is configured separately.

Dockerless containers are a separate bootstrap case: before their image filesystem is built, core can use the fixed `/.dockerless/bin/sh` bundle when `DOCKERLESS=true`, `/bin/sh` is not executable, and that bundled shell is executable. `/bin/sh` remains preferred when available. This does not change the SSH host prerequisite above.

The host needs standard bootstrap tools, including `mkdir`, `mktemp`, `head` with `-c`, `wc`, `chmod`, `mv`, and `rm`. A download uses `curl` or `wget`; when neither is available, Devsy can transfer the agent over the SSH connection. The agent directory must permit execution and either be writable by the account or allow noninteractive privilege escalation.

Both the external OpenSSH client and the built-in SSH transport use the same bootstrap launcher; switching transports does not repair a missing `/bin/sh` or a restricted account.

For locked-down accounts, ask the administrator to permit `/bin/sh` and the required tools, provide a writable executable agent directory, and check forced-command restrictions. Keep noninteractive shell startup output off stdout: it carries the bootstrap protocol and the live SSH tunnel. Send diagnostics to stderr and limit banners and prompts to interactive sessions.

### VS Code SSH connection timeout

If Remote - SSH reports `Connection timed out during banner exchange`, a slow provider connection can exceed its default timeout. Increase `remote.SSH.connectTimeout` in VS Code user settings, for example to `60` seconds, and reconnect. This applies to all Remote - SSH hosts.

### Workspace waits for the Devsy agent

If container logs repeatedly report `waiting for devsy agent to be available`, check whether the container's `DEVSY_AGENT_PATH` exists and whether its agent volume is mounted. A container created without the agent mount must be recreated after updating Devsy; restarting it cannot change its mounts.

Recreating a container discards changes in its writable layer. Back up any data outside persistent workspace mounts before recreating it.

### Fish startup configuration

Anything in `config.fish` runs on every `fish -c` call, which can interfere with `devsy internal agent workspace up`. Move your customizations inside the `if status is-interactive` block:

```
if status is-interactive
    eval "$(/home/linuxbrew/.linuxbrew/bin/brew shellenv)"
    # customizations
end
```

### SELinux

With SELinux, a mounted volume can fail with "Permission denied" even when ownership is correct. Add `:Z` to the volume:

```json
{
    "workspaceMount": "",
    "workspaceFolder": "/workspaces/${localWorkspaceFolderBasename}",
    "runArgs": [
        "--volume=${localWorkspaceFolder}:/workspaces/${localWorkspaceFolderBasename}:Z"
    ]
}
```

### Generic application icon on GNOME

GNOME on Wayland associates a running application with an installed desktop entry. Devsy uses the desktop filename `sh.devsy.app.desktop` and window identity `sh.devsy.app`. Flatpak exports a theme icon named `sh.devsy.app`; electron-builder's DEB/RPM packages retain the icon name `devsy-desktop`. The icon name must match the package's desktop entry, not necessarily its application ID.

Directly executing an AppImage does not install its embedded desktop entry. Choose **Add to applications** in the first-launch prompt, or open **Settings > Applications menu**. Devsy writes `$XDG_DATA_HOME/applications/sh.devsy.app.desktop` and copies the 128-pixel icon to `$XDG_DATA_HOME/icons/hicolor/128x128/apps/sh.devsy.app.png` (default data home: `~/.local/share`). The launcher uses the permanent AppImage path, never its temporary mount.

Declining leaves the AppImage usable, but a generic or ungrouped GNOME Wayland icon can remain until desktop integration is installed. If a third-party integrator already manages this AppImage, keep using that integration; Devsy reports the existing launcher rather than creating a duplicate. An existing system or Flatpak Devsy launcher also blocks installation. Remove the conflicting installation or manage its launcher yourself before retrying.

If you move the AppImage, launch it once from its new path to update Devsy's owned launcher automatically. Settings also offers **Update launcher** and **Remove**. Paths containing `=` cannot be represented in a desktop launcher; move the AppImage to another path. Read-only data directories and other integration failures are reported without preventing normal Devsy use.

If you edit a launcher created by Devsy, Devsy leaves the entire edited file unchanged, including during updates or removal. Settings reports the conflict; manage that launcher manually or move it aside before using **Add to applications** again. A customized, shared or pre-existing icon is preserved when repairing or re-adding a launcher and is not claimed for later deletion.

For manual integration, both the desktop entry and a persistent icon file must be installed. Do not reference an icon inside `/tmp/.mount_*`: it disappears when the AppImage exits. Use the package-specific icon name described above, or copy an icon to the user's icon-theme directory and reference that name. Refreshing the icon cache alone cannot repair a missing desktop entry or asset.

After upgrading from v1.24.0, an old pinned launcher may still reference a previous desktop filename. Unpin that launcher and pin Devsy again. Check the applications directories for older `devsy-desktop.desktop` entries before creating another launcher; do not delete entries owned by another package.

### `ENAMETOOLONG` when opening a workspace in VS Code

Some distributions have a very long `PATH`, which makes the SSH connection string too long. Set the SSH binary explicitly in VS Code. See [issue #1045](https://github.com/devsy-org/devsy/issues/1045).

### Docker permission denied or daemon unreachable

If `devsy workspace up` fails with a permission error on `docker.sock`, add your user to the `docker` group and log in again:

```sh
sudo usermod -aG docker $USER
```

If the daemon is not running, start it:

```sh
sudo systemctl start docker
```

### Podman

#### Rootless socket

Rootless Podman uses the socket `$XDG_RUNTIME_DIR/podman/podman.sock`. If Devsy cannot connect, start the user socket:

```sh
systemctl --user start podman.socket
```

Or point Devsy at it:

```sh
devsy provider set podman --option PODMAN_HOST=unix:///run/user/$(id -u)/podman/podman.sock
```

#### `podman compose`

`podman compose` hands off to an external provider, either `podman-compose` or a standalone `docker-compose`. Install one:

```sh
sudo apt-get install -y podman-compose
```

Install it on the host that runs Podman to support Compose-based workspaces. If scripts inside the workspace container call `docker-compose` or `podman compose`, install those tools in the container too.

#### BuildKit syntax

`podman build` uses buildah, so Dockerfiles with the `# syntax=docker/dockerfile:1` line or `RUN --mount` fail. Remove the syntax line and avoid BuildKit mounts.

#### Volume permissions in rootless mode

Rootless Podman maps user IDs, so files created in the container can appear owned by `nobody` on the host. With SELinux, use `:Z` as above. Without it, fix ownership:

```sh
podman unshare chown -R $(id -u):$(id -g) /path/to/volume
```
